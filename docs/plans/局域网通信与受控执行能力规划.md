# 局域网通信与受控执行能力规划

## 背景

MochiDesk 当前已经具备以下基础：

- Tauri 桌面壳与 Rust 原生模块边界
- `src-tauri/src/commands/` 的统一命令注册入口
- `src/lib/services/` 的前端原生能力封装模式
- `src/lib/models/` 与 `src/lib/animation/` 的状态模型承接能力
- 以“小木藕”桌宠为中心的状态反馈与轻交互形态

下一阶段希望扩张的后端能力主要有两类：

1. 基于局域网的 Mochi 之间轻量通信
2. 本机受控任务执行，例如拉代码、跑服务、做检查

目标不是提前做成远控平台、脚本平台或复杂多机编排系统，而是在当前桌面 MVP 的边界内，为“两个 Mochi 互相感知”和“本机代办任务”建立清晰、可控、可逐步演进的基础能力。

## 当前实现边界

### 当前已实现

- `src-tauri/src/monitor/`
  已承担系统与 Codex 状态读取
- `src-tauri/src/commands/`
  已承担 Tauri 命令注册与暴露
- `src/lib/services/`
  已承担前端到原生能力的收口
- `src/lib/models/`
  已开始承接状态模型

### 当前未实现

- 局域网 socket 通信
- Peer 发现与在线列表
- 网络消息协议
- 本机任务白名单执行器
- 任务运行日志流
- “远端请求，本地确认后执行”的能力链路

## 目标原则

- 优先服务桌面端 MVP，不做公网通信、远程编排或复杂控制台
- 优先固定边界，不开放“前端传任意 shell 字符串直接执行”
- 优先做局域网轻量消息，不提前做可靠传输、文件传输或 NAT 穿透
- 优先做受控任务执行，而不是泛化脚本平台
- UDP 消息不直接触发命令执行，真正执行任务必须经过本机明确授权或本机主动触发
- 前端继续只依赖 `services` 和模型层，不直接散落 Tauri 调用

## 能力分层建议

建议把后端扩展拆成两个独立模块，而不是混在 `monitor` 中继续堆：

### 1. `network`

负责：

- UDP 监听与发送
- Peer 发现
- 消息协议解析
- 最近消息缓存
- Peer 在线状态维护

不负责：

- 任意任务执行
- 权限确认 UI
- 动画表现策略

### 2. `task_runner`

负责：

- 可执行任务清单
- 任务启动、停止、状态流转
- stdout / stderr / exit code 收集
- 并发限制与超时控制

不负责：

- 网络收发
- Peer 管理
- 任意 shell 透传

## 一、局域网 UDP 能力规划

## 目标

让两个或多个 Mochi 在同一局域网内能够：

- 发现彼此
- 维持在线状态
- 发送轻量状态消息
- 发送简单交互事件

不要求：

- 强一致
- 可靠投递
- 跨公网
- 文件同步

## 为什么第一版适合 UDP

- 轻量
- 实现成本低
- 适合广播与发现
- 很适合“在线 / 打招呼 / 轻事件”这类桌宠场景

当前阶段不建议先做 TCP 或 WebSocket 常驻连接作为主链路，因为那会更快把系统推向“服务编排”而不是“桌宠互相感知”。

## UDP 第一版消息模型

建议所有消息使用 JSON，并显式带版本号。

建议结构：

```ts
interface LanMessage<T = Record<string, unknown>> {
  version: 1;
  type: "hello" | "heartbeat" | "status" | "interaction" | "request" | "bye";
  senderId: string;
  senderName: string;
  timestamp: number;
  payload: T;
}
```

### 建议的第一版消息类型

- `hello`
  用于广播上线与主动发现
- `heartbeat`
  用于保活
- `status`
  用于同步轻状态，例如 `idle / busy / notice`
- `interaction`
  用于同步轻交互，例如 `wave / poke / notice`
- `request`
  用于发送“希望对方执行某项本地动作”的请求，但不直接执行
- `bye`
  用于下线通知

## Peer 模型建议

```ts
interface LanPeer {
  id: string;
  name: string;
  address: string;
  port: number;
  lastSeenAt: number;
  status: "online" | "stale";
  activity: "idle" | "thinking" | "acting" | "waiting_input" | "notice" | "busy";
}
```

作用：

- `id / name` 用于前端展示和去重
- `address / port` 用于回发消息
- `lastSeenAt / status` 用于判断是否掉线
- `activity` 用于桌宠之间最小状态同步

## UDP 第一阶段建议命令

- `start_udp_listener(port?: number)`
- `stop_udp_listener()`
- `broadcast_udp_message(message: LanMessage)`
- `send_udp_message(target: string, message: LanMessage)`
- `get_known_peers()`
- `get_recent_network_events()`

建议再提供事件通道：

- `lan://peer-updated`
- `lan://message-received`

## UDP 第一阶段建议行为

1. 启动监听后自动广播一次 `hello`
2. 周期性广播 `heartbeat`
3. 收到 `hello / heartbeat` 时更新 peer 列表
4. Peer 超过一定时间未刷新时标记为 `stale`
5. 前端只读取 peer 列表与最近事件，不直接接触 socket 细节

## 当前不建议纳入第一版的 UDP 能力

- 广播之外的复杂发现协议
- 可靠重传
- 文件发送
- 大消息分片
- 加密协商
- 公网穿透

## 二、受控任务执行能力规划

## 目标

允许 MochiDesk 在本机执行少量明确任务，例如：

- `git pull`
- `pnpm dev`
- `pnpm check`
- `cargo check`

同时满足：

- 可追踪
- 可停止
- 有日志输出
- 不开放任意命令透传

## 不建议的实现方式

当前阶段不建议支持：

- 前端传入任意 shell 字符串并直接执行
- UDP 消息直接触发 shell
- 无固定工作目录的自由执行
- 不带超时和状态管理的裸进程启动

这些做法会很快把项目推向高风险、难维护的方向。

## 建议的任务模型

第一版建议使用“任务白名单执行器”。

## 三、局域网触发的远程技能能力规划

## 背景场景

当前新增的真实使用场景是：

- 一台 `Mac` 机器主要负责编码与提交
- 一台 `Windows` 机器主要负责拉取仓库并运行服务
- 两台机器通过 `git` 同步代码
- `Mac` 在完成推送后，通过局域网消息通知 `Windows`
- `Windows` 收到后，在本机执行固定部署流程，例如拉代码并重启服务

目标不是做成通用远控平台，而是在当前桌面 MVP 内，为“双机开发 + 单机运行”建立一条可控、可追踪、可回传状态的最小远程技能链路。

第一项远程技能明确为：

- `deploy-project`

## 设计原则

- UDP 只负责传递技能执行意图，不直接承载任意命令
- 远端消息不能携带任意 shell 字符串并直接执行
- 真正的执行逻辑来自接收端本地预配置的 remote skill profile
- 每条技能请求都必须能映射到唯一技能、唯一项目和唯一目标机器
- 每次技能请求必须有 `requestId`，便于去重、回传和排错
- 必须有最小鉴权，至少校验目标机器和共享密钥
- 必须有结果回传，不能只做“发出去就不管了”

## 推荐消息模型

建议在现有 UDP 协议上新增部署相关消息类型：

- `deploy_announce`
- `deploy_ack`
- `deploy_progress`
- `deploy_result`

推荐 payload 结构：

```ts
interface RemoteSkillRequestPayload {
  requestId: string;
  skillId: string;
  projectId: string;
  targetMachineId: string;
  branch: string;
  commit: string;
  serviceName: string;
  token: string;
}
```

其中：

- `requestId`
  用于一次技能请求的唯一标识
- `skillId`
  用于标识具体执行哪项远程技能，例如 `deploy-project`
- `projectId`
  映射接收端本地 deployment profile
- `targetMachineId`
  防止同局域网其他 Mochi 误响应
- `branch / commit`
  用于让接收端明确要部署哪个版本
- `serviceName`
  用于标识本地将被重启的服务
- `token`
  作为第一版最小鉴权字段

## 接收端 remote skill profile 设计

不建议让网络消息直接决定命令内容。建议在接收端本地维护固定 profile，例如：

```ts
interface RemoteSkillProfile {
  skillId: string;
  projectId: string;
  machineId: string;
  paths: {
    repoRoot: string;
    tauriRoot?: string;
    serviceRoot?: string;
  };
  branch: string;
  sharedToken: string;
  updateMode: "ff_only" | "reset_hard";
  tasks: {
    fetchTaskId: string;
    pullTaskId?: string;
    stopServiceTaskId: string;
    startServiceTaskId: string;
  };
}
```

作用：

- `skillId` 用于标识这是哪种远程技能
- `projectId` 用来匹配网络请求和本地项目
- `machineId` 用来确认消息是否发给当前机器
- `paths.repoRoot` 用来确定主仓库工作目录
- `paths.tauriRoot / paths.serviceRoot` 用来为后续多目录技能预留执行上下文
- `updateMode` 用来区分保守更新和强制部署
- `tasks.*` 用来复用本地白名单任务体系，而不是绕开任务系统

当前实现建议优先让：

- `pull-project` 使用 `paths.repoRoot`
- `start-service / restart-service` 使用 `paths.serviceRoot`
- 后续如有 Rust 专属技能，再逐步接入 `paths.tauriRoot`

## 推荐部署状态机

接收端建议把一次技能执行拆成明确状态：

1. `received`
2. `validating`
3. `fetching`
4. `pulling`
5. `stopping_service`
6. `starting_service`
7. `waiting_ready`
8. `success`
9. `failed`

其中 `deploy-project` 技能建议使用这套状态机。

这样：

- 接收端本地可以展示每一步
- 发起端可以看到卡在什么阶段
- 失败时可以明确是 Git 失败、停服务失败，还是服务没 ready

## Git 更新策略建议

对于 `deploy-project` 技能，建议显式支持两种模式：

### 1. `ff_only`

执行策略：

- `git fetch origin`
- `git checkout <branch>`
- `git pull --ff-only origin <branch>`

适合：

- 接收端偶尔也会手动改动代码
- 希望优先保护本地工作区

### 2. `reset_hard`

执行策略：

- `git fetch origin`
- `git checkout <branch>`
- `git reset --hard origin/<branch>`

适合：

- 纯运行机
- 希望部署结果稳定一致
- 接收端原则上不保留手工改动

第一版如果明确 `Windows` 机器只是运行机，推荐使用 `reset_hard`，但必须做成 profile 里的显式配置，不能默认偷偷启用。

## 与现有任务系统的衔接建议

当前任务系统已经具备：

- 白名单任务
- 后台运行
- 停止任务
- 服务任务 `ready` 识别

因此远程技能能力不建议另起一套执行器，而应在任务系统上增加“复合技能任务”概念。

建议 `deploy-project` 技能执行器内部按步骤调用受控任务，例如：

1. 运行 `git fetch`
2. 按 profile 选择 `git pull --ff-only` 或 `git reset --hard`
3. 停止当前服务任务
4. 启动服务任务
5. 等待服务任务进入 `ready`

## MVP 范围建议

第一版只做下面这条最小闭环：

- 单技能
- 单项目
- 单目标机器
- 单固定分支
- 单固定服务
- 共享密钥校验
- 发起端发送远程技能请求
- 接收端自动执行 remote skill profile
- 接收端通过 UDP 回发结果

第一版不做：

- 任意项目动态选择
- 任意命令动态下发
- 多机编排
- 复杂权限系统
- 公网通信
- 文件同步

## 三、网络与执行的安全边界

这是本次规划里最需要提前定死的部分。

### 必须明确禁止

- UDP 消息直接执行 shell
- 远端 Mochi 未经确认直接执行本机任务
- 自由透传命令、参数和工作目录
- 局域网消息直接映射到高权限系统操作

### 第一版允许的联动方式

更安全的链路是：

1. 远端发送 `request`
2. 本地 Mochi 显示提醒
3. 本机用户明确确认
4. 本地 `task_runner` 执行白名单任务

这样可以保留“两个 Mochi 协作”的产品感觉，同时不把系统变成局域网远控入口。

## 四、推荐实施顺序

### 阶段 1：UDP 最小链路

目标：

- 能监听 UDP
- 能广播与发送 JSON 消息
- 能维护 peer 列表
- 能在前端看见最近消息

完成标志：

- 两台机器上的 Mochi 能互相发现
- peer 列表能稳定显示在线状态

### 阶段 2：桌宠联动

目标：

- 把 peer 状态映射到 Mochi 的轻提示或轻互动
- 支持 `wave / notice / hello` 之类的轻交互

完成标志：

- 一个 Mochi 发出轻事件，另一个 Mochi 能在桌面上给出简短反馈

### 阶段 3：本机任务白名单执行器

目标：

- 列出可执行任务
- 启动任务并返回运行状态
- 输出 stdout / stderr
- 能停止长任务

完成标志：

- 本机可以通过前端稳定触发 `git pull`、`pnpm check` 等任务

### 阶段 4：远端请求，本地确认

目标：

- UDP `request` 消息进入本地审批流
- 本地确认后才进入 `task_runner`

完成标志：

- 两个 Mochi 可以协作发起“请求”，但执行边界仍然留在本机

## 五、前端表现建议

当前阶段不建议为此新增复杂控制台页面。

更适合的方式是：

- 先做一个很轻的开发态调试面板
- 显示在线 peer 数量
- 显示最近 3 到 5 条网络事件
- 显示最近任务状态

后续如果能力稳定，再决定是否做单独的“联机 / 任务”设置页。

## 六、当前不建议做的事情

- 不做公网通信
- 不做自由 shell
- 不做复杂任务编排
- 不做大而全的插件系统
- 不做多协议同时并进
- 不做“网络控制台 + 脚本平台 + 桌宠平台”三者混合的巨型基础设施

## 七、建议的下一步落地项

如果下一轮开始实作，最推荐先做：

1. 建立 `network` Rust 模块骨架
2. 定义 `LanMessage / LanPeer` 前后端模型
3. 实现 UDP listener + broadcast 的最小链路
4. 暴露 `get_known_peers()` 与最近消息接口
5. 前端做一个极简开发态联机调试入口

等这条链路稳定后，再进入 `task_runner`。
